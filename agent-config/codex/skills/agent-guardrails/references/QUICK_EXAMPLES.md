# QUICK_EXAMPLES

## 什么时候先问

### 示例 1：需求有歧义

用户说：“给职位配置支持审批。”

先不要直接加状态字段、审批流、MQ。
先问：

1. 审批是单人还是多人？
2. 只改后端状态，还是要补接口与消息流转？
3. 成功标准是什么？

### 示例 2：边界不明确

用户说：“把查询接口优化一下。”

先问：

1. 是优化响应时间、SQL、返回字段，还是接口结构？
2. 允许改查询条件和返回结构吗？
3. 如何判断优化成功？

## 什么时候直接做

### 示例 3：单点小改且上下文充分

用户说：“把 `JobConfigVO` 的 `name` 改成 `jobName`，前端已经同步了。”

如果影响范围清楚，且只需同步少量 Convert / VO / 测试，可直接做，不必额外追问。

### 示例 4：明确 bug 修复

用户说：“`status = null` 时这里 NPE，帮我修一下。”

若报错位置、预期行为都清楚，可直接补空值保护和针对性验证。

## 什么时候需要短计划

### 示例 5：多文件实现

用户说：“新增职位发布接口，并发送 MQ 通知测评服务。”

先给 2-4 步短计划：

1. 确认接口、Service、MQ 影响面
2. 做最小必要实现
3. 补充或运行针对性验证

### 示例 6：代码审查

用户说：“帮我 review 这次改动。”

先说明审查重点：

1. correctness / 回归风险
2. 事务、缓存、MQ、多实例安全
3. 测试缺口
4. 最后再看风格和命名

## 什么时候不要擅自扩大改动

### 示例 7：顺手重构诱惑

用户让你给某个 Controller 加一个字段。

即使你看到邻近 Service 命名不规范、Mapper 可以抽公共方法，也不要直接顺手改；除非这些问题会直接导致本次需求无法落地或无法验证。

更合适的做法是：

1. 先完成当前需求的最小必要改动
2. 明确提醒用户这里还有可顺手优化点
3. 由用户决定是否把优化并入本次任务

### 示例 8：测试最小化

用户让你修一个空指针问题。

优先补一个能复现该空指针的测试或最小验证，不要顺手重写整套测试类。
