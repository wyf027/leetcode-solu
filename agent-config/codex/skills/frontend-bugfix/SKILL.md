# 前端 Bug 修复模式

**加载时机：** 任务类型判断为"修某个具体 bug / 修某个具体问题"时加载。  
**职责：** 最小改动、根因定位、等价验证。禁止在此模式中做任何 cleanup、重构、抽象。

**进入此模式时必须声明：**
```
【任务判断】
- 任务类型：Bug 修复
- 执行路径：Bug 修复模式
- 本次禁止：cleanup / 重构 / 抽象 / 文件迁移
```

---

## 一、执行三步骤

### 步骤 1：定位根因（不是修改现象）

- 先读调用链，追踪 bug 的真实触发路径
- 明确说明根因：是哪一行代码、哪一个条件、哪一个数据导致了问题
- **禁止在未确认根因时开始写代码**

根因定位输出格式：
```
【根因定位】
- 触发路径：（组件 → hook → 接口 / 状态变化链）
- 根因：（具体说明是哪一行/条件/数据导致问题）
- 为什么之前没有问题：（如果适用）
```

### 步骤 2：最小改动修复

- 只修改与问题直接相关的代码
- 不允许因"顺路看到了"就改无关代码
- **改动范围：原则上 ≤ 3 个文件、≤ 20 行**
- 超出范围时，参考 frontend-governance.mdc 中的扩展修改模式声明

### 步骤 3：验证等价性

- 修复后确认其他入口、其他状态下的行为未被影响
- 对于 loading/状态类 bug：确认 loading 只影响触发源，不影响无关组件
- 对于数据类 bug：确认修复路径上的所有消费点

---

## 二、Bug 类型速查表

| Bug 类型 | 第一步检查 |
|---|---|
| loading 联动（多个按钮同时 loading） | 检查 loading 来源是否为全局 boolean，是否需要改为 ID 级别 |
| 双 toast | 搜 `message.error/success`，确认是否 hook + page 各触发一次 |
| 弹窗数据残留 | 检查关闭时是否执行了 `resetForm` + `clearDetail` |
| 字段空白 / undefined 渲染 | 确认字段是否有 `?? '-'` 兜底 |
| ID 精度丢失 | 确认是否在某处做了 `Number(id)` 转换 |
| 表单回填错误 | 确认 `setFieldsValue` 数据来源是否经过 normalize/mapper |
| 接口参数错误 | 确认 payload 组装点，检查字段类型与值 |
| 蓝块 / 默认值闪现 | 确认编辑态 state 是否在 detail 回填前被清空 |
| Select 无法选中 | 确认 option.value 类型与 form value 类型是否一致（string vs number） |
| 表单关闭后残留旧数据 | 确认关闭时是否执行了 resetFields + 清理业务 state |

## 三、验证闭环（修复后必须执行）

修复完成后，必须验证以下四项并在输出中明确说明：

### 1. 原问题是否被修复
- 复现路径上的 bug 是否消失
- 修复的根因是否被真正解决（而不只是绕过现象）

### 2. 原有行为是否保持等价
- 修复前的正常路径，修复后是否依然正常
- 修复前其他入口/模式下的行为，修复后是否未受影响

### 3. 是否影响以下四个维度（逐项确认）
- **表单行为**：回填是否正常，提交是否完整
- **提交流程**：payload 字段是否完整，接口参数是否正确
- **UI 展示**：字段显示是否正确，三态（loading/empty/error）是否正常
- **状态流转**：modal 开关、loading 变化、数据刷新是否按预期

### 4. 验证输出格式

```
【验证结果】
- 原问题：已修复 / 未修复（说明原因）
- 等价性：未破坏 / 存在影响（列出影响点）
- 表单行为：正常 / 异常（说明）
- 提交流程：正常 / 异常（说明）
- UI 展示：正常 / 异常（说明）
- 状态流转：正常 / 异常（说明）
```

## 四、禁止行为（Bug 修复模式中严格禁止）

- **禁止顺手 cleanup**（"既然改了这里，顺便把这里也重构一下"）
- **禁止引入新抽象**（"这里应该抽成 hook，顺便改了"）
- **禁止文件迁移**（"这个函数放在这里不对，顺便移过去"）
- **禁止修改用户可见行为**（如修改文案、调整布局——除非这就是 bug 本身）
- **禁止在未确认根因时开始写代码**
- **禁止改变接口参数结构**（除非接口参数错误本身是 bug）

---

## 五、发现无关问题时的处理

修复过程中发现了其他代码问题但不在本次 bug 范围内：
- 不修改
- 在输出末尾列出：
  ```
  【发现但未处理的问题】
  - path/to/file.ts：（问题描述，建议下一轮第 X 轮 cleanup 处理）
  ```
- 留给用户决定后续如何处理

---

## 六、难以定位根因时的处理

若按步骤 1 追踪调用链后仍无法确认根因，触发安全回退策略：

```
【安全回退】
- 停止原因：无法确定根因，追踪到 ___ 层后路径不清晰
- 已完成的分析：（已读过的文件/调用链）
- 当前假设：（可能的根因，但未确认）
- 未完成的部分：（分析中断，根因未确认，修复暂停）
- 需用户确认的问题：
  1. ___ 的预期行为是什么？
  2. ___ 字段的正确类型是什么？
- 推荐下一步：（等待确认 / 提供更多调用链上下文）
```
