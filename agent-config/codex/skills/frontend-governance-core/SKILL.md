# 前端工程治理 · 核心调度器

**加载时机：** 任何前端代码治理任务（cleanup / bug 修复 / 重构 / 定向优化）开始时，第一个加载此文件。  
**职责：** 判断任务类型 → 选路径 → 输出强制声明 → 决定是否停止 / 回退 / 分解。

---

## 版本冻结说明（v1.3.1）

- **当前版本已进入实战验证阶段。** 所有规则与执行方法已稳定，不再新增内容，不再调整结构。
- **非明确问题不得修改 Skill / Rule。** 执行过程中发现的优化想法，统一记录到索引文件的"问题记录"区域，不直接改规则。
- **所有优化需求先记录，不立即改规则。** 问题积累后统一评审，通过版本升级流程（如 v1.4.0）处理。

## 一、适用场景

- 对某业务目录做 cleanup / 重构 / 收敛
- 修某类业务 bug（loading 联动、双 toast、弹窗残留、字段空白、ID 精度丢失等）
- 统一某类交互一致性（空态、错误态、未实现入口、禁用规则）
- 不确定任务归属，需要先判断再分派

---

## 二、执行决策流程（最高优先级，必须第一步执行）

**禁止在未输出任务判断声明之前开始任何代码修改。**

```
接到任务
    │
    ├─ 是"修 bug / 修某个具体问题"？
    │       └─→ 进入【Bug 修复模式】→ 加载 frontend-bugfix/SKILL.md
    │           禁止进入 cleanup 分轮
    │           禁止结构性重构
    │
    ├─ 是"整体 cleanup / 重构"？
    │       └─→ 按分轮策略执行 → 加载 frontend-cleanup-playbook/SKILL.md
    │           每次只允许执行一轮
    │           禁止混轮次修改
    │
    └─ 是"定向优化某类问题"？（有明确归属）
            ├─ 数据问题（字段混乱/ID 精度/payload 散落）→ 第二轮
            ├─ 状态/副作用问题（双 toast/loading 联动/弹窗残留）→ 第三轮
            ├─ UI/交互问题（空白字段/未实现入口/三态缺失）→ 第四轮
            └─ 类型/稳定性问题（any 污染/竞态/memo 滥用）→ 第五轮
```

**核心约束：**
- 每次只允许执行一轮，不允许在同一次会话中混合多个轮次
- Bug 修复模式与 cleanup 分轮互斥
- 不确定归属时，先做第一轮（删冗余），再诊断后续归属

### 强制声明（禁止跳过）

每次任务开始，**先输出以下声明，再动手写代码：**

```
【任务判断】
- 任务类型：Bug 修复 / 整体 Cleanup 第 N 轮 / 定向优化（第 X 轮）
- 执行路径：Bug 修复模式 / 按分轮策略
- 本次禁止的行为：___
- 参考 Skill：（frontend-bugfix / frontend-cleanup-playbook）
```

Bug 修复时必须包含：
- "进入 Bug 修复模式"
- "本次禁止：cleanup / 重构 / 抽象 / 文件迁移"

## 三、分层职责参考图

> 所有 Skill 和 Rule 的职责判断以此图为基准。修改前检查改动是否符合对应层的职责边界。

```
┌──────────────────────────────────────────────────────────┐
│  page / layout                                           │
│  职责：组装 + 编排 + 路由参数处理                           │
│  不允许：写业务逻辑、写 payload、做 API 字段拼接            │
├──────────────────────────────────────────────────────────┤
│  controller hook（useXxxPage）                           │
│  职责：整合子 hooks，暴露稳定 handlers、modal 状态          │
│  不允许：直接写 JSX、有 DOM 副作用                          │
├──────────────────────────────────────────────────────────┤
│  domain hook（useXxxList / useAddXxx 等）                 │
│  职责：数据请求、副作用、单一业务操作、loading/error 处理    │
│  不允许：跨域操作、UI 渲染逻辑                              │
├──────────────────────────────────────────────────────────┤
│  normalize 层（xxxNormalize.ts）                         │
│  职责：API 响应 → 前端消费结构，字段 fallback，枚举转换      │
│  不允许：有副作用、发请求                                   │
├──────────────────────────────────────────────────────────┤
│  mapper 层（mappers.ts）                                 │
│  职责：结构 A → 结构 B 的字段映射，候选人/选项/表单预填转换  │
│  不允许：业务判断、副作用                                   │
├──────────────────────────────────────────────────────────┤
│  component（UI 组件）                                    │
│  职责：接收稳定 props，渲染，触发事件                       │
│  不允许：自行 fetch、散落 payload 组装、复制 mapper 逻辑    │
├──────────────────────────────────────────────────────────┤
│  utils（纯函数工具）                                      │
│  职责：无副作用的纯函数（格式化、计算、映射）                │
│  不允许：import hooks、引用 store、调用 API                │
└──────────────────────────────────────────────────────────┘
```

## 四、停止优化条件

当满足以下所有条件时，**必须停止优化**。继续是过度工程化的信号。

**检查清单：**

- [ ] 无明显冗余代码（无死代码、无重复逻辑、无未使用的 state/handler）
- [ ] 数据流单一（normalize → mapper → setFieldsValue → buildXxxParams，无散落）
- [ ] 状态来源唯一（modal open/close 只在一处、loading 只在一处）
- [ ] 无双 toast / loading 混乱（每个请求只有一处处理）
- [ ] UI 行为一致（三态统一、nullable 字段均有兜底）
- [ ] 无明显边界问题（弹窗关闭有 reset、未实现入口有 disabled 或隐藏）

**满足后禁止继续：**

- 禁止为"更优雅"重构已工作良好的代码
- 禁止为"更统一"强行合并各自正确的代码
- 禁止为"更抽象"封装只用一次的逻辑
- 禁止为"更干净"全局 rename（扩大无意义 diff）
- 禁止无测量依据添加 `memo` / `useMemo` / `useCallback`

**判断依据：改动是否让代码更可维护、更可验证、更易 review。答案不明确时，停止。**

### 停止条件强制输出

每轮结束时必须输出：

```
【停止条件评估】
- 无冗余代码：是 / 否（还有：___）
- 数据流单一：是 / 否（还有：___）
- 状态来源唯一：是 / 否（还有：___）
- 无双 toast：是 / 否（还有：___）
- UI 行为一致：是 / 否（还有：___）
- 无边界问题：是 / 否（还有：___）

结论：已达到停止条件 / 未达到，建议下一轮处理：___
【是否继续优化】：停止 / 建议下一轮（说明：___）
```

## 五、安全回退策略

**出现不确定性时，优先停止而非继续。宁可中断等待确认，不可盲目修改。**

### 必须停止的触发条件

| 触发条件 | 具体表现 |
|---|---|
| 无法确定根因 | 追踪调用链后仍不清楚 bug 的真实触发路径 |
| 修改可能影响核心链路 | 改动文件同时被多个页面/功能使用（如公共 hook、共享 mapper） |
| 类型不明确 | 字段类型在接口定义和实际使用中存在矛盾 |
| 多方案不确定 | 存在 2 种以上修复路径，各有取舍，无法独立决策 |
| 验证路径不清晰 | 修复后无法确定如何验证等价性 |

### 触发后必须输出

```
【安全回退】
- 停止原因：（触发条件 + 具体描述）
- 已完成的修改：（已改动文件和内容）
- 未完成的部分：（剩余任务描述）
- 需用户确认的问题：
  1. ___
  2. ___
- 推荐下一步：（等待确认 / 提供更多上下文 / 拆分为更小任务）
```

> 注：Bug 修复场景下使用 frontend-bugfix 中的专属格式（含"当前假设"字段）。

### 已有部分改动时

- 独立且正确的改动：保留，声明"已完成部分可提交"
- 依赖未完成部分的改动：建议回滚，声明"建议暂不提交"
- 禁止留下"半完成状态"代码（类型已改但逻辑未更新、mapper 已改但消费方未更新）

## 六、复杂任务分解策略

**超出单次执行能力时，必须主动分解，不强行在一次会话中完成所有内容。**

### 触发分解的条件

满足任意一条必须先分解：

- 涉及 3 个以上模块（page + hooks + components + mapper 同时需要改动）
- 超出修改范围默认限制，且不满足扩展修改模式的单一触发条件
- 同时涉及第二轮（收数据流）+ 第三轮（收状态与副作用）+ 第四轮（收交互一致性）的混合问题
- 无法在一次 review 中理解全部改动意图

### 分解原则

1. **按维度拆分，不按文件拆分**
   - 正确：先"数据流收敛"→ 再"状态收敛"→ 再"UI 统一"
   - 错误：先改 A 文件 → 改 B 文件 → 改 C 文件（维度混乱）

2. **每个子任务独立可验证**（可单独 lint / tsc / 手工验证）

3. **禁止跨轮次混合**：每个子任务只属于一个轮次

4. **输出分解计划再执行**：

```
【任务分解计划】
当前任务：___
子任务 1：___（目标：___，预计文件：___）
子任务 2：___（目标：___，预计文件：___）
子任务 3：___（目标：___，预计文件：___）

本次执行：子任务 1
执行完成后：请确认后继续子任务 2
```

## 七、输出格式规范

### 模式判断（先选模式，再输出）

**轻量模式条件（三项全部满足）：**
1. 本次修改 ≤ 1 个文件
2. 无副作用风险（纯删冗余、纯 `?? '-'` 补充、纯注释修改）
3. 非结构变更（不涉及接口 / hook 返回值 / props 类型变化）

不满足任意一条 → 使用完整模式。

---

### 轻量模式

```
【轻量输出】
- 任务类型：（Bug 修复 / Cleanup 第 N 轮）
- 修改文件：path/to/file.tsx
- 修改内容：（1-3 行 bullet）
- 验证结果：（Prettier ✓ / Lints ✓ / 行为等价 ✓）
```

---

### 完整模式（6 项缺一不可）

**1. 任务判断**
```
【任务判断】
- 任务类型：Bug 修复 / 整体 Cleanup 第 N 轮 / 定向优化（第 X 轮）
- 执行路径：Bug 修复模式 / 按分轮策略
- 本次禁止：___
```

**2. 执行策略**
- 本轮目标（一句话）
- 执行范围（只做什么，不做什么）
- 诊断结论（发现了哪些问题，哪些不做）

**3. 修改文件范围**
```
【修改文件列表】
- path/to/file1.ts（原因：___）
- path/to/file2.tsx（原因：___）

【发现但未处理的问题】（留待下一轮）
- path/to/file3.ts（问题：___）
```

**4. 修改内容**
- 删除了什么（冗余/死代码）
- 收敛了什么（重复逻辑/散落 payload）
- 修复了什么（bug/边界）
- 新增了什么关键注释

**5. 验证结果**
```
【验证清单】
- [ ] 原有功能正常（列出验证的主路径）
- [ ] 修改后行为等价
- [ ] loading/empty/error 态正常
- [ ] 提交流程正常
- [ ] 表单回填正常（如有）
```

**6. 停止条件评估**（使用第四节格式）
