Core insight

尾零来自 10，而阶乘里真正稀缺的是因子 5

每个尾零需要一个 10 = 2 × 5。阶乘中的偶数远多于 5 的倍数，所以 2 总是充足，答案就是 n! 的质因子分解中 5 的指数。

⌊n/5⌋ 统计至少含一个 5 的数；⌊n/25⌋ 为 25 的倍数补上第二个 5；继续加上 ⌊n/125⌋、⌊n/625⌋…，直到商为 0。

Formula card

⌊n/5⌋ + ⌊n/25⌋ + ⌊n/125⌋ + …

iteration
n ← floor(n / 5)
accumulate
answer ← answer + n
stop
n = 0

完整过程

  1. 01 / PAIR

    一个尾零对应一对因子 2 和 5；只需数更少的 5。

  2. 02 / COUNT

    整除 5 得到这一层至少含一个新 5 的数量。

  3. 03 / ADD

    把商加入答案；它还代表下一层需要继续检查的数量。

  4. 04 / SHRINK

    持续 n = floor(n/5)，商归零时结束。

边界与溢出

  • n < 5 时第一次整除即为 0，答案为 0。
  • n = 25 要计 5 个普通倍数和额外的第二个 5，共 6。
  • 直接反复除以 5 不做乘法，因此不会出现 power *= 5 的整数溢出。
  • 在官方范围内答案小于 n，32 位整数足够。

复杂度与追问

每轮把 n 缩小为原来的 1/5，只执行 O(log₅ n) 次；除结果变量外使用 O(1) 空间。这正面满足官方“对数时间”追问。

也可以遍历每个 5 的倍数并数其 5-adic valuation，但至少需要 O(n/5) 次外层迭代，不如分层整除直接。

为什么不直接算阶乘

n! 增长极快，普通整数很快溢出；即使用大整数，乘法和存储完整阶乘也远超只统计因子的需求。

  • 浮点阶乘会丢失末尾精确信息。
  • 转字符串再数 0 需要先承担巨大的计算与内存成本。
  • 反复删除十进制零仍没有解决阶乘生成本身。

面试追问与常见错误

为什么 2 不用统计？

每两个数就有一个 2，而每五个数才有一个 5；阶乘里 2 的指数严格更多。

为什么 25 要多算一次？

25 = 5²，第一次 ⌊n/5⌋ 只计了其中一个，⌊n/25⌋ 补上第二个。

常见 off-by-one 是什么？

把循环写成 current ≥ 5 没问题，但若先累加后除会错误加入原始 n；应先整除再累加。

若输入扩大到 64 位？

相同的反复除法仍安全；避免显式构造 5 的幂即可消除乘法溢出点。

class Solution {
    public int trailingZeroes(int n) {
        int answer = 0;
        while (n > 0) {
            n /= 5;
            answer += n;
        }
        return answer;
    }
}

var trailingZeroes = function (n) {
    let answer = 0;
    while (n > 0) {
        n = Math.floor(n / 5);
        answer += n;
    }
    return answer;
};
