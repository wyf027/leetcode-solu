盈利计划

人数是背包容量，利润是需要跨过的门槛。真正的难点不是“利润越大越好”，而是如何在不重复使用工作的前提下，准确统计所有可行子集。

困难数组动态规划0-1 背包非付费题

题目

有 n 名成员和若干项工作。第 i 项工作需要 group[i] 名互不复用的成员，并产生 profit[i] 利润。选择工作的任意子集；若使用人数不超过 n，且总利润至少为 minProfit，这个子集就是一个盈利计划。

任务：返回不同盈利计划的数量。答案可能很大，需要对 10^9 + 7 取模。

函数形式

profitableSchemes(n, minProfit, group, profit) → integer

示例 1

输入：n = 5, minProfit = 3,
      group = [2,2], profit = [2,3]
输出：2
解释：可选择工作 {1} 或 {0,1}。

示例 2

输入：n = 10, minProfit = 5,
      group = [2,3,5], profit = [6,7,8]
输出：7
解释：任意非空工作子集均满足，共 7 种。

约束

  • 1 ≤ n ≤ 100
  • 0 ≤ minProfit ≤ 100
  • 1 ≤ group.length ≤ 100
  • 1 ≤ group[i] ≤ 100
  • profit.length == group.length
  • 0 ≤ profit[i] ≤ 100

核心洞察

我们只关心利润是否达到门槛，而不关心超过门槛多少。因此将实际利润 x 映射到 min(x, minProfit)。定义 dp[j][k]：处理过若干工作后，恰好使用 j 人、封顶利润为 k 的方案数。

dp[j][min(minProfit, k + earn)] += dp[j - need][k]

初始只有空集：dp[0][0] = 1。每项工作只能选择一次，所以原地更新时 j 必须倒序；k 也倒序，使本轮新状态不会再次成为同一工作的来源。答案是 Σ dp[j][minProfit]，其中 0 ≤ j ≤ n。

完整过程

  1. 建立大小为 (n + 1) × (minProfit + 1) 的计数表。
  2. 放入空集状态 dp[0][0] = 1。
  3. 依次考察每项工作，其人数为 need、利润为 earn。
  4. 人数从 n 递减到 need，利润档从 minProfit 递减到 0。
  5. 把“不选”的原状态保留，并把“选当前工作”的方案累加到新状态，随时取模。
  6. 汇总利润档为 minProfit 的所有人数状态。

正确性证明

  1. 状态不变量。处理前 i 项工作后，dp[j][k] 精确等于从这 i 项中选取、恰好用 j 人且封顶利润为 k 的子集数。初始时只有空集，故成立。
  2. 转移完整且无重。任何处理到当前工作的子集，要么不包含它（原状态保留），要么包含它（从不含当前工作的旧状态加上人数与利润）。两类互斥且覆盖全部子集；倒序更新保证当前工作不会被重复选择。
  3. 封顶不影响判定。所有实际利润不少于 minProfit 的状态都映射到同一档，恰好对应“达到门槛”；低于门槛的利润仍被精确保留。
  4. 结论。全部工作处理完后，不超过 n 人且达到门槛的方案，恰好分布在 dp[0…n][minProfit] 中，求和即为答案。

复杂度与边界

设工作数为 m，时间复杂度 O(m · n · minProfit)，空间复杂度 O(n · minProfit)。

  • minProfit = 0 时，空集也是合法方案，初始化会自然计入。
  • 单项工作人数大于 n 时无法被选择，循环自然跳过。
  • profit[i] = 0 仍可能形成不同子集，不能忽略。
  • 每次累加都取模；JavaScript 使用 Number 时两个模数内值相加仍远低于整数精度上限。

四语言完整代码

class Solution {
    public int profitableSchemes(int n, int minProfit,
                                 int[] group, int[] profit) {
        final int MOD = 1_000_000_007;
        int[][] dp = new int[n + 1][minProfit + 1];
        dp[0][0] = 1;

        for (int i = 0; i < group.length; i++) {
            int need = group[i], earn = profit[i];
            for (int people = n; people >= need; people--) {
                for (int p = minProfit; p >= 0; p--) {
                    int nextProfit = Math.min(minProfit, p + earn);
                    dp[people][nextProfit] = (int) (
                        (dp[people][nextProfit]
                         + (long) dp[people - need][p]) % MOD
                    );
                }
            }
        }

        long answer = 0;
        for (int people = 0; people <= n; people++) {
            answer = (answer + dp[people][minProfit]) % MOD;
        }
        return (int) answer;
    }
}

替代方案、面试追问与常见错误

替代方案

可以使用三维 DP 显式保留“处理到第几项工作”，更容易理解但空间为 O(mnP)；也可每轮复制二维表并正序更新，逻辑安全但额外复制成本更高。

面试追问

  • 若成员可以复用，转移顺序如何改变？
  • 若要求利润恰好等于门槛，还能封顶吗？
  • 怎样恢复某个具体计划？
  • 为什么“至多 n 人”最后需要跨人数求和？

常见错误

  • 把人数状态误定义为“至多”，导致重复累计。
  • 正序更新，令同一工作被选多次。
  • 只返回 dp[n][P]，遗漏少于 n 人的方案。
  • 忘记 minProfit = 0 下的空集。
