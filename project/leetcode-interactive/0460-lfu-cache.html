LFU 缓存

在容量受限的缓存里，淘汰“使用频率最低”的键；频率相同，再淘汰最久未使用者。两种优先级必须同时成立，而每次操作仍需保持平均常数时间。

Problem

题意与接口

设计 LFUCache 类。缓存为每个键维护使用次数；新插入键的次数为 1，命中的 get 以及对已有键的 put 都会令次数加 1。

接口定义

  • LFUCache(int capacity)：以容量 capacity 初始化。
  • int get(int key)：键存在则返回值并增加其频率，否则返回 -1。
  • void put(int key, int value)：已有键则更新值并增加频率；新键插入前若已满，先淘汰频率最低的键。最低频率并列时，淘汰其中最久未使用的键。

要求：get 与 put 都具备平均 O(1) 时间复杂度。

约束

  • 1 ≤ capacity ≤ 104
  • 0 ≤ key ≤ 105
  • 0 ≤ value ≤ 109
  • 最多调用 2 × 105 次 get 与 put

Solution

双层哈希：频率桶 + 桶内 LRU

把“找最低频率”和“同频淘汰最久未使用”拆成两个都能常数时间维护的问题。

核心洞察

①
key → 条目

哈希表直接定位键的值、当前频率，以及它在当前频率桶中的位置。

②
freq → 有序键集合

每个频率维护独立 LRU 顺序。左端最久未使用，右端最近使用；删除任意键、追加到右端、弹出左端都为平均 O(1)。

③
minFreq

始终记录缓存内最低频率。淘汰时无需扫描所有频率，直接进入对应桶。

④
一次命中 = 搬桶

从频率 f 的桶删除键，频率加一，再追加到 f + 1 桶的 MRU 端。

完整过程

  1. get(key)：若键不存在返回 -1；否则保存值，执行一次“提升频率”，再返回值。
  2. put 已有键：覆盖旧值，然后同样执行“提升频率”。题意明确规定，对已有键的 put 也算一次使用。
  3. put 新键且已满：从 minFreq 桶的 LRU 端移除一个键，并同步从条目表删除。
  4. 插入新键：频率设为 1，放到频率 1 桶的 MRU 端，并令 minFreq = 1。
  5. 更新 minFreq：提升键后，只有当旧桶正是最低频率桶且变空时，才将 minFreq 加 1。

正确性证明

不变式 A：每个缓存键恰好出现在其当前频率对应的桶中。插入时键进入频率 1 桶；每次命中都从旧桶删除并进入频率加一后的桶，因此始终成立。

不变式 B：每个频率桶内部按使用时间从旧到新排列。插入或命中的键都追加到 MRU 端，其余键相对次序不变，因此桶首始终是该频率下最久未使用的键。

不变式 C：minFreq 等于缓存中的最低频率。新键插入时最低频率必为 1；提升操作只可能让当前最低桶变空，此时最低值恰好增加 1；其他情况不改变最低频率。

缓存满时，算法从 minFreq 桶的 LRU 端淘汰。由 A、C 可知它具有全局最低频率；由 B 可知它又是该频率下最久未使用的键。因此淘汰结果严格符合 LFU 规则及 LRU 平局规则。

复杂度与边界

项目结论原因
get平均 O(1)哈希定位、桶内删除与追加均为平均常数时间。
put平均 O(1)淘汰直接访问 minFreq 桶，无全局扫描。
空间O(capacity)每个缓存键在条目表与一个频率桶中各保存一次。
  • 容量为 0：虽然官方约束从 1 开始，代码仍防御性地让 put 直接返回。
  • key 或 value 为 0：它们都是合法值，不能用真假判断代替“是否存在”。
  • 更新已有键：不仅改值，还必须增加使用频率并刷新同频 LRU 次序。
  • get 未命中：返回 -1，不创建条目，也不改变任何频率桶。
  • 频率桶变空：只在它等于 minFreq 时推进 minFreq；空桶本身可保留或删除。

方案复杂度取舍

面试追问

为什么 minFreq 只需加 1，而不是向上扫描？

提升一个位于最低频率 f 的键时，它只会进入 f + 1。若 f 桶因此变空，至少刚提升的键就在 f + 1 桶，所以新的最低频率必为 f + 1。

生产环境如何处理频率无限增长？

可周期性衰减所有频率、设置计数上限，或按时间窗口重建统计。题目不要求衰减，但真实缓存需要避免历史热度永久压制新热点。

如何做并发安全？

最直接是用一把锁保护条目表、频率桶和 minFreq 的复合更新。更高吞吐可做分片 LFU，但严格的全局淘汰顺序会变得更昂贵。

为什么不能只维护一个全局 LRU 链表？

单一 LRU 只表达最近性，无法 O(1) 找到最低频率。即使节点保存频率，也仍需扫描或维护额外有序结构。

常见错误清单

  • 把已有键的 put 当成只改值，遗漏频率提升。
  • 频率并列时随意淘汰，没有在桶内维护 LRU 顺序。
  • 淘汰后忘记从条目表删除，留下幽灵键或错误 size。
  • 提升键后无条件增加 minFreq，导致跳过仍非空的最低频率桶。
  • 新键插入后忘记将 minFreq 重置为 1。
  • 使用普通数组或链表按 key 查找，表面上桶操作 O(1)，整体却退化到 O(n)。
