哲学家进餐

The Dining Philosophers

MEDIUM多线程5 位哲学家5 把叉子非付费题

01 / PROBLEM

先把问题看清楚

这里展示接口与并发约束；解法刻意留到页面底部。

5 位哲学家按顺时针编号 0～4，围坐在圆桌旁。相邻两人之间只有一把叉子。哲学家在思考与进餐之间交替，但只有同时持有自己的左叉和右叉时才能进餐；一把叉子同一时刻只能由一个人持有，吃完后必须归还两把叉子。

请为共享的 DiningPhilosophers 对象设计并发规则，使每个请求都能完成：不能死锁，也不能让某个哲学家永久挨饿。5 个线程会同时调用下列函数，同一哲学家的新调用甚至可能在上一次结束前到来。

wantsToEat( philosopher, pickLeftFork, pickRightFork, eat, putLeftFork, putRightFork )

回调契约

  • pickLeftFork / pickRightFork：拿起该哲学家的对应叉子。
  • eat：只能在两把叉子均已拿到后调用。
  • putLeftFork / putRightFork：归还对应叉子。
  • 未发起进餐请求时，哲学家被视为正在思考。

关键事实

输入n：每位哲学家调用函数的次数
范围1 ≤ n ≤ 60
竞争叉子 i 位于哲学家 i 与相邻哲学家之间
目标互斥、无死锁、无饥饿
输出并非函数返回值，而是回调产生的事件序列

事件格式：[a,b,c]，a 为哲学家；b 为叉子（1 左、2 右，吃时为 0）；c 为操作（1 拿、2 放、3 吃）。合法调度不唯一。

官方示例

输入：n = 1

输出：[[3,2,1],[3,1,1],[3,0,3],[3,1,2],[3,2,2],[4,2,1],[4,1,1],[2,2,1],[2,1,1],[1,2,1],[2,0,3],[2,1,2],[2,2,2],[4,0,3],[4,1,2],[4,2,2],[1,1,1],[1,0,3],[1,1,2],[1,2,2],[0,1,1],[0,2,1],[0,0,3],[0,1,2],[0,2,2]]

解释：n 表示每位哲学家需要进餐的次数。
output[i] = [a,b,c]
- a：哲学家编号
- b：叉子，1 表示左叉，2 表示右叉；吃面事件使用 0
- c：操作，1 表示拿起，2 表示放下，3 表示进餐
例如 [4,2,1] 表示 4 号哲学家拿起右叉。
线程调度顺序不固定，所以其他满足约束的事件顺序同样正确。

04 / SOLUTION

FIFO 票号 + 单通道进餐

这是一种以并行度换取证明简单度的方案：请求按到达顺序逐个完成。

核心洞察

与其同时管理 5 把叉子的复杂依赖，不如把“一次完整进餐”视作唯一共享资源。每个请求先领取递增票号，只有票号等于当前服务号的请求可以执行五个回调。完成后服务号加一，并唤醒下一批等待者。

临界阶段的回调顺序是：拿左叉 → 拿右叉 → 吃 → 放右叉 → 放左叉。由于任意时刻只有一个请求进入该阶段，两把目标叉子必然空闲。

完整过程

  1. 在条件变量保护下领取唯一票号 myTicket = nextTicket++。
  2. 当 myTicket != serving 时等待；条件必须用循环检查，以抵抗虚假唤醒。
  3. 轮到自己后释放排队锁，依次调用拿叉、进餐与放叉回调。
  4. 重新持有排队锁，将 serving 加一并唤醒所有等待线程。

互斥与安全性

服务号在任何时刻只对应一张票。因而至多一个请求操作叉子，不会出现共享叉，也不会在缺少任一叉子时调用 eat。

无死锁

当前服务者无需等待任何其他哲学家释放叉子；完成后必定推进服务号。资源等待图中不存在环。

无饥饿

票号严格递增并按序服务。假设已进入临界阶段的回调会结束、等待线程最终能被调度，则每张有限票号都会轮到。

同人并发调用

队列记录的是“调用”而不是“哲学家”。即便同一编号同时出现多次，每次也有独立票号，不会混淆。

复杂度与边界

  • 每次调用时间：不计排队与回调耗时，协调开销为 O(1)；使用广播唤醒时会有额外调度成本。
  • 空间：共享状态 O(1)；等待队列由运行时维护，最多与并发请求数成正比。
  • 边界：n=1 与 n=60 使用同一逻辑；哲学家 0 与 4 的相邻关系不需要特殊分支。
  • 假设：题目提供的回调正常返回。若回调可能抛异常，工程实现应在 finally / RAII 清理路径中推进队列并释放已拿资源。

官方可提交语言。条件变量实现严格 FIFO 票号队列。

import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

class DiningPhilosophers {
    private final ReentrantLock queueLock = new ReentrantLock();
    private final Condition turnChanged = queueLock.newCondition();
    private long nextTicket = 0;
    private long serving = 0;

    public DiningPhilosophers() {}

    public void wantsToEat(int philosopher,
                           Runnable pickLeftFork,
                           Runnable pickRightFork,
                           Runnable eat,
                           Runnable putLeftFork,
                           Runnable putRightFork) throws InterruptedException {
        long myTicket;

        queueLock.lockInterruptibly();
        try {
            myTicket = nextTicket++;
            while (myTicket != serving) {
                turnChanged.await();
            }
        } finally {
            queueLock.unlock();
        }

        try {
            pickLeftFork.run();
            pickRightFork.run();
            eat.run();
            putRightFork.run();
            putLeftFork.run();
        } finally {
            queueLock.lock();
            try {
                serving++;
                turnChanged.signalAll();
            } finally {
                queueLock.unlock();
            }
        }
    }
}

LeetCode 本题官方元数据未提供 JavaScript 提交模板；以下为本地异步语义参考，不宣称可直接提交。

class DiningPhilosophers {
  constructor() {
    // Promise 链天然按加入顺序串行执行。
    this.tail = Promise.resolve();
  }

  wantsToEat(
    philosopher,
    pickLeftFork,
    pickRightFork,
    eat,
    putLeftFork,
    putRightFork
  ) {
    const runOneTurn = async () => {
      await pickLeftFork();
      await pickRightFork();
      await eat();
      await putRightFork();
      await putLeftFork();
    };

    const current = this.tail.then(runOneTurn, runOneTurn);
    // 即使某次回调失败，也让后续请求能够继续排队。
    this.tail = current.catch(() => undefined);
    return current;
  }
}

官方可提交语言。使用 threading.Condition 管理票号。

from threading import Condition
from typing import Callable


class DiningPhilosophers:
    def __init__(self):
        self.cv = Condition()
        self.next_ticket = 0
        self.serving = 0

    def wantsToEat(
        self,
        philosopher: int,
        pickLeftFork: Callable[[], None],
        pickRightFork: Callable[[], None],
        eat: Callable[[], None],
        putLeftFork: Callable[[], None],
        putRightFork: Callable[[], None]
    ) -> None:
        with self.cv:
            my_ticket = self.next_ticket
            self.next_ticket += 1
            while my_ticket != self.serving:
                self.cv.wait()

        try:
            pickLeftFork()
            pickRightFork()
            eat()
            putRightFork()
            putLeftFork()
        finally:
            with self.cv:
                self.serving += 1
                self.cv.notify_all()

官方可提交语言。condition_variable 等待谓词处理虚假唤醒。

#include <condition_variable>
#include <cstdint>
#include <functional>
#include <mutex>

using namespace std;

class DiningPhilosophers {
private:
    mutex queueMutex;
    condition_variable turnChanged;
    uint64_t nextTicket = 0;
    uint64_t serving = 0;

public:
    DiningPhilosophers() = default;

    void wantsToEat(int philosopher,
                    function<void()> pickLeftFork,
                    function<void()> pickRightFork,
                    function<void()> eat,
                    function<void()> putLeftFork,
                    function<void()> putRightFork) {
        uint64_t myTicket;
        {
            unique_lock<mutex> lock(queueMutex);
            myTicket = nextTicket++;
            turnChanged.wait(lock, [&] { return myTicket == serving; });
        }

        pickLeftFork();
        pickRightFork();
        eat();
        putRightFork();
        putLeftFork();

        {
            lock_guard<mutex> lock(queueMutex);
            ++serving;
        }
        turnChanged.notify_all();
    }
};

替代方案

至多 4 人竞争

用容量为 4 的信号量打破环形等待，可保留较高并发；公平性取决于信号量和叉子锁的调度策略。

奇偶反向拿叉

奇数先左后右、偶数先右后左，可破坏统一环路；实现轻量，但饥饿证明需要额外公平假设。

服务员监控器

只在两把叉子同时空闲时批准进餐，能让不相邻哲学家并行；状态管理和公平队列更复杂。

面试追问

  • 为什么不直接给 5 把叉子分别加锁？ 因为互斥只能保证安全，不能自动消除五方循环等待。
  • 如何提升吞吐？ 使用带 FIFO 等待队列的“服务员”，一次批准互不相邻的请求，理论上最多两人并行进餐。
  • notify_one 可以吗？ 票号方案中被唤醒的线程未必正好持有下一票，简单实现应使用 notify_all；或改成每个请求独立条件变量。
  • 真实系统还要考虑什么？ 取消、超时、回调异常、线程中断、监控指标与锁竞争性能。

常见错误

  • 每个人都先拿左叉再拿右叉，形成经典死锁。
  • 用 if 代替 while 检查条件，忽略虚假唤醒。
  • 拿到一把叉子后长期等待另一把，降低系统活性。
  • 忘记在异常路径释放资源或推进队列。
  • 把“测试运行未死锁”误当成数学意义上的无饥饿证明。
