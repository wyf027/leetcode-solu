核心洞察：先有全部组合，再统计实际记录

只对现有记录 GROUP BY，无法凭空生成未出现的组合。先构造三个平台与三个实验名称的笛卡尔积，就得到一张永远有 9 行的骨架；再左连接实验表，按组合统计真实记录。

  1. 建立 Platforms 与 Names 两个固定维表，各包含三个互不重复的值。
  2. CROSS JOIN 生成 9 个组合，作为左表。
  3. 按平台和实验名称两个条件 LEFT JOIN Experiments，保留没有匹配的组合。
  4. 按左表的两个维度分组，计算 COUNT(e.experiment_id)。

为什么不能用 COUNT(*)？未匹配组合仍然有一行右侧为 NULL 的占位记录；COUNT(*) 会把它算成 1。COUNT(e.experiment_id) 忽略 NULL，所以得到 0。

MySQL 8+ · 官方数据库语言提交方案

WITH Platforms AS (
    SELECT 'Android' AS platform
    UNION ALL SELECT 'IOS'
    UNION ALL SELECT 'Web'
), Names AS (
    SELECT 'Reading' AS experiment_name
    UNION ALL SELECT 'Sports'
    UNION ALL SELECT 'Programming'
)
SELECT p.platform,
       n.experiment_name,
       COUNT(e.experiment_id) AS num_experiments
FROM Platforms AS p
CROSS JOIN Names AS n
LEFT JOIN Experiments AS e
  ON e.platform = p.platform
 AND e.experiment_name = n.experiment_name
GROUP BY p.platform, n.experiment_name;

正确性

覆盖：两个固定维表的笛卡尔积让每个合法组合恰好出现一次，因此最终分组不会遗漏任何组合，也不会产生额外组合。

计数：设某组合有 k 条真实记录。当 k > 0，两个连接条件恰好匹配这 k 条记录，主键都非空，COUNT 得到 k；当 k = 0，左连接保留一条右侧为 NULL 的行，COUNT 得到 0。每个组合的计数都正确，因而整个结果正确。

边界与常见错误

  • 空输入也要返回 9 行，且全部为 0；不能从事实表 SELECT DISTINCT 取维度。
  • 同组合、不同 ID 是多次实验，应全部累加；无需 COUNT(DISTINCT platform)。
  • 不要使用 INNER JOIN，它会丢弃计数为 0 的组合。
  • 连接必须同时匹配 platform 与 experiment_name；只匹配一个字段会串组。
  • 按左侧维度分组；若使用右侧字段，缺失组合可能被归入同一 NULL 组。
  • 不要在 WHERE 中添加要求右表字段非空的条件，否则会滤掉空匹配。输出无需排序，IOS 拼写遵循题目。

复杂度与替代方案

设记录数为 N。语义模型只需扫描 N 条记录并输出 9 个计数，时间 O(N + 9)，计数空间 O(9)，即固定域下 O(N) 时间、O(1) 额外空间。SQL 实际时间与内存由连接策略、分组实现和索引决定：固定 9 组的嵌套扫描约 O(9N)，排序聚合可能达到 O(N log N)，不能保证所有执行计划都是线性。

替代方案一：先按组合聚合 Experiments，再把聚合结果左连接到 9 行骨架，并用 COALESCE(count, 0) 补零，可减少连接中间行。替代方案二：对 9 个组合分别做相关 COUNT 子查询，语义直接，但可能多次扫描。生产场景若类别不是固定的，应使用完整维表；不能依赖事实记录是否出现。

面试追问

  • 新增平台怎么办？扩展平台维表，而不是从已有实验推断允许的平台。
  • 按日期筛选如何保留零？在右表子查询中先过滤，或将日期条件放进 ON；骨架仍作左表。
  • 如何支持大表？考虑先聚合，结合 (platform, experiment_name) 索引与数据库执行计划分析；本页未执行性能验证。
  • 何时需要 COALESCE？直接 COUNT 忽略空值后自然为 0；连接预聚合的计数列时，空匹配计数列是 NULL，需补零。
