终止一个进程，
也终止它的整棵子树。

父进程关系天然构成一棵树。先理解“终止传播”的方向，再用交互演示观察队列如何逐层收集所有后代。

Problem

题目描述

函数：killProcess

系统中有 n 个进程。数组 pid 给出每个进程的唯一编号，位于相同下标的 ppid[i] 表示 pid[i] 的父进程编号；根进程的父编号为 0。

给定要终止的进程编号 kill，返回所有会被终止的进程编号：包括 kill 本身，以及它的全部直接或间接子进程。返回顺序不限。

输入签名： killProcess(pid: List<int>, ppid: List<int>, kill: int) -> List<int>

示例 1

输入：pid = [1,3,10,5], ppid = [3,0,5,3], kill = 5
输出：[5,10]

进程 5 的直接子进程是 10，因此终止 5 会同时终止 10。

示例 2

输入：pid = [1], ppid = [0], kill = 1
输出：[1]

唯一进程既是根，也是要终止的进程。

约束

  • n == pid.length == ppid.length
  • 1 <= n <= 5 × 104
  • 1 <= pid[i] <= 5 × 104，且所有 pid 互不相同
  • 0 <= ppid[i] <= 5 × 104
  • 恰有一个进程的父编号为 0；其余进程各有一个父进程，整体关系构成一棵树
  • kill 一定出现在 pid 中

    Solution

    哈希表建树 + BFS

    核心洞察

    输入给的是“子 → 父”

    但终止会从父进程传播到所有子进程，所以先把关系反转为 父 → 子列表。

    答案就是一棵子树

    从 kill 开始做 BFS 或 DFS，能到达的所有节点恰好都是要终止的进程。

    完整过程

    1. 同步遍历 pid 与 ppid，把每个 pid[i] 加入 children[ppid[i]]。
    2. 将 kill 放入队列。
    3. 队列非空时取出一个进程，加入答案；再将它的全部直接子进程入队。
    4. 队列清空后，所有直接和间接后代都已被收集，返回答案。题目允许任意顺序。

    正确性证明

    完备性： kill 首先入队。若某个应被终止的进程已被访问，它的每个直接子进程都会入队；沿父子路径归纳，kill 的所有后代最终都会被访问并加入答案。

    可靠性： 算法只从 kill 出发，且只沿父到子的边移动，因此加入答案的每个进程都是 kill 本身或其后代，都确实应被终止。

    综上，返回集合与所有应被终止的进程集合完全相同。

    复杂度

    设总进程数为 n。建邻接表扫描一次，BFS 每个相关节点和父子边至多处理一次，因此时间复杂度为 O(n)；邻接表、队列与答案占用 O(n) 额外空间。

    边界情况

    • kill 是叶子：答案只有它自己。
    • kill 是根：整棵树都会被收集。
    • 树退化为长链：迭代 BFS 不受递归栈深限制。
    • 某个进程有大量直接子进程：邻接表能一次取得全部孩子。

    四种语言完整代码

    JavaBFS · O(n)
    class Solution {
    public List<Integer> killProcess(
            List<Integer> pid,
            List<Integer> ppid,
            int kill) {
        Map<Integer, List<Integer>> children = new HashMap<>();

        for (int i = 0; i < pid.size(); i++) {
            children
                .computeIfAbsent(ppid.get(i), key -> new ArrayList<>())
                .add(pid.get(i));
        }

        List<Integer> result = new ArrayList<>();
        Deque<Integer> queue = new ArrayDeque<>();
        queue.offer(kill);

        while (!queue.isEmpty()) {
            int current = queue.poll();
            result.add(current);

            for (int child : children.getOrDefault(
                    current, Collections.emptyList())) {
                queue.offer(child);
            }
        }

        return result;
    }
}
    JavaScriptBFS · O(n)
    /**
 * @param {number[]} pid
 * @param {number[]} ppid
 * @param {number} kill
 * @return {number[]}
 */
var killProcess = function(pid, ppid, kill) {
    const children = new Map();

    for (let i = 0; i < pid.length; i++) {
        if (!children.has(ppid[i])) {
            children.set(ppid[i], []);
        }
        children.get(ppid[i]).push(pid[i]);
    }

    const result = [];
    const queue = [kill];
    let head = 0;

    while (head < queue.length) {
        const current = queue[head++];
        result.push(current);

        for (const child of children.get(current) || []) {
            queue.push(child);
        }
    }

    return result;
};
    PythonBFS · O(n)
    from collections import defaultdict, deque
from typing import List


class Solution:
    def killProcess(
        self,
        pid: List[int],
        ppid: List[int],
        kill: int
    ) -> List[int]:
        children = defaultdict(list)

        for child, parent in zip(pid, ppid):
            children[parent].append(child)

        result = []
        queue = deque([kill])

        while queue:
            current = queue.popleft()
            result.append(current)
            queue.extend(children[current])

        return result
    C++BFS · O(n)
    class Solution {
public:
    vector<int> killProcess(
        vector<int>& pid,
        vector<int>& ppid,
        int kill
    ) {
        unordered_map<int, vector<int>> children;

        for (int i = 0; i < static_cast<int>(pid.size()); ++i) {
            children[ppid[i]].push_back(pid[i]);
        }

        vector<int> result;
        queue<int> pending;
        pending.push(kill);

        while (!pending.empty()) {
            int current = pending.front();
            pending.pop();
            result.push_back(current);

            for (int child : children[current]) {
                pending.push(child);
            }
        }

        return result;
    }
};

    替代方案与取舍

    DFS

    同样是 O(n)。递归写法更短，但极深的进程链可能触发调用栈限制；显式栈可规避。

    反复扫描 ppid

    每处理一个父进程都重扫数组，最坏会退化到 O(n²)，不适合 5 × 104 的规模。

    常见错误

    • 沿 pid → ppid 向上寻找祖先，方向与终止传播相反。
    • 只加入直接子进程，遗漏更深层后代。
    • 忘记把 kill 本身加入答案。
    • 使用 Array.shift() 实现 JavaScript 队列，可能带来不必要的数组搬移；用头指针更稳妥。
    • 误以为答案必须按编号排序；题目允许任意顺序。

    面试追问

    如果会连续执行很多次 kill 查询呢？

    邻接表只建一次，每次从对应节点遍历子树。如果还要求避免重复终止，可维护进程存活状态，并在查询后更新结构或跳过已终止节点。

    如果输入不是一棵树，而是一般有向图呢？

    遍历时必须增加 visited 集合，避免环造成无限循环，也避免一个节点经多条路径重复加入答案。

    如何保留父进程先于子进程的输出顺序？

    BFS 和前序 DFS 都天然会先输出当前父节点，再探索它的孩子。若还要求同层固定顺序，可在建表后对每个孩子列表排序。
