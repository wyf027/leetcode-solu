01 · Problem contract

先定义这个小世界

实现一个简化版 Twitter：用户可以发布推文、关注或取消关注其他用户，并查询由自己与关注者发布的最近 10 条推文。结果必须从新到旧排列。

类与方法

00
Twitter()
初始化简易 Twitter 对象。
01
void postTweet(int userId, int tweetId)
用户发布一条新推文；每次传入的 tweetId 唯一。
02
List<Integer> getNewsFeed(int userId)
返回该用户信息流中最近 10 条推文 ID，按时间从新到旧。
03
void follow(int followerId, int followeeId)
followerId 开始关注 followeeId。
04
void unfollow(int followerId, int followeeId)
followerId 取消关注 followeeId。

约束

  • 1 ≤ userId, followerId, followeeId ≤ 500
  • 0 ≤ tweetId ≤ 10⁴
  • 所有推文 ID 互不相同。
  • 四个公开方法合计最多调用 3 × 10⁴ 次。
  • 用户不能关注自己。
返回范围：信息流只包含用户本人和当前关注者的推文；取消关注后，对方的推文应立即从新查询中消失。

官方示例

完整参数形式
输入
["Twitter", "postTweet", "getNewsFeed", "follow", "postTweet", "getNewsFeed", "unfollow", "getNewsFeed"]
[[], [1, 5], [1], [1, 2], [2, 6], [1], [1, 2], [1]]

输出
[null, null, [5], null, null, [6, 5], null, [5]]

解释
Twitter twitter = new Twitter();
twitter.postTweet(1, 5); // 用户 1 发布推文 5
twitter.getNewsFeed(1);  // 返回 [5]
twitter.follow(1, 2);    // 用户 1 关注用户 2
twitter.postTweet(2, 6); // 用户 2 发布推文 6
twitter.getNewsFeed(1);  // 返回 [6, 5]，因为推文 6 更新
twitter.unfollow(1, 2);  // 用户 1 取消关注用户 2
twitter.getNewsFeed(1);  // 返回 [5]

04 · Solution

多路归并，不扫描世界

核心洞察

每个用户的推文按时间从新到旧形成一条链表。查询 User 1 时，候选来源只有 User 1 本人与其当前关注者。每条链表内部已经有序，因此不必把所有历史推文收集后再整体排序；只需比较每条链的当前队首。

最大堆里始终只放“每条候选时间线尚未取出的最新节点”。弹出最晚节点后，把它在同一条链上的 next 放回堆。重复最多 10 次，就是答案。

完整过程

  1. 保存状态。用哈希表记录每个用户的推文链表头，用哈希集合记录每个用户关注了谁，并维护严格递增的全局时间戳。
  2. 发布推文。创建含 tweetId、time、next 的节点，令 next 指向该用户原链表头，再更新链表头。
  3. 改变关注。follow 向集合插入 followeeId；unfollow 从集合删除。集合操作天然适合重复调用。
  4. 初始化查询堆。把用户本人以及每位关注者的链表头放入按 time 降序的最大堆；空链跳过。
  5. 多路归并。最多执行 10 次：弹出堆顶，把 tweetId 加入答案；若该节点有 next，就把 next 压入堆。

正确性证明

不变式

每次循环开始时，对于每条仍有未输出推文的候选时间线，堆中恰好包含该时间线最新的未输出节点。

初始化

查询开始时，每条非空时间线的链表头就是该时间线最新推文，全部被加入堆，因此不变式成立。

保持

堆顶时间戳最大，所以它是所有候选时间线中全局最新的未输出推文。输出它之后，该链的 next 成为这条时间线最新的未输出节点；把 next 加入堆后，其他时间线候选不变，不变式继续成立。

终止

循环在输出 10 条或堆为空时停止。根据不变式，每次输出的都是当时全局最新项，故答案严格从新到旧；若堆为空，所有合法推文均已输出。因此结果恰为信息流中最近的至多 10 条推文。

边界与复杂度

  • 用户没有推文且未关注任何人时，返回空列表。
  • 本人无需加入自己的关注集合；查询时始终显式加入本人时间线。
  • 重复关注只保留一条集合关系；重复取消不存在的关系不产生影响。
  • 取消关注只改变后续查询的候选来源，无需删除对方的历史推文。
  • 全局时间戳只用于比较先后；tweetId 唯一但不代表时间顺序。

复杂度：设某用户关注数为 F，推文总数为 T，关注边数为 E。发布、关注、取消关注平均为 O(1)。查询初始化 O(F)，随后最多 10 次堆操作，时间为 O(F + 10 log(F + 1))；查询临时空间 O(F)，持久空间 O(T + E)。

替代方案

收集后排序：查询时收集本人和所有关注者的全部推文，再按时间排序并截取前 10。实现直观，但历史推文越多越慢，单次查询可达 O(T log T)。

全局时间线倒序扫描：维护所有推文的全局列表，查询时从后向前找作者合法的前 10 条。活跃用户少时可接受，但若最近大量推文都来自未关注用户，扫描会很深。

写扩散 Feed Cache：发推时把推文推送给所有粉丝，读操作很快，却让高粉丝用户的写入成本爆炸，还需要复杂的一致性与缓存淘汰。本题规模下，多路归并是更均衡的选择。

面试追问

  • 如果时间戳溢出怎么办？使用 64 位整数，或以单调序列号加分片 ID 形成可比较键。
  • 真实分布式系统如何生成全局顺序？可讨论 Snowflake ID、逻辑时钟以及“近似时间序”与严格全序的取舍。
  • 关注者达到百万级怎么办？需要分页、候选裁剪、活跃作者索引，甚至针对普通用户写扩散、名人读扩散的混合策略。
  • 删除推文如何处理？链表可加 tombstone，查询弹出时跳过；后台再做压缩回收。
  • 如何支持翻页？返回最后一条的复合游标，并在下一次查询中只考虑早于游标的节点。

常见错误

  • 用 tweetId 比较新旧；题目只保证它唯一，不保证递增。
  • 忘记把用户自己的推文加入信息流。
  • 把自己永久塞进关注集合，导致 follow / unfollow 语义混乱。
  • 最大堆弹出节点后没有压入同链 next，于是每个作者最多出现一条推文。
  • 先遍历所有历史推文再排序，忽略结果最多只有 10 条这一关键信息。
  • Java 比较器直接相减，在更大时间戳范围下可能整数溢出；应使用 Comparator 或 Integer.compare。
