#1583 MEDIUM
Count Unhappy Friends

统计不开心的朋友

一组配对已经确定，但每个人心里都有自己的亲近顺序。你的任务不是重新配对，而是判断：有多少人会因为存在一组“彼此更偏好”的关系而不开心。

数组模拟n 为偶数本地交互页
Problem

题意

返回整数

给定偶数 n 位朋友。preferences[i] 按从高到低记录朋友 i 对其余人的亲近顺序；pairs 把每个人恰好配入一对。若 x 与 y 配对，同时存在另一位与 v 配对的朋友 u，并且下面两个条件同时成立，则 x 不开心。

1x 更偏好 u在 x 的偏好列表中，u 排在当前搭档 y 前面。
2u 也更偏好 x在 u 的偏好列表中，x 排在 u 的当前搭档 v 前面。
目标：统计不开心的朋友数量。这里只判断每个朋友是否不开心，同一个人即使有多个见证者也只计数一次。

约束

  • 2 ≤ n ≤ 500，且 n 为偶数
  • preferences.length == n
  • preferences[i].length == n - 1
  • 0 ≤ preferences[i][j] ≤ n - 1
  • preferences[i] 不含 i，且元素互不相同
  • pairs.length == n / 2
  • pairs[i].length == 2，且同一对中的两人不同
  • 每个人恰好出现在一个配对中

Full solution

把“更偏好”变成常数时间比较

O(n²)

核心洞察

偏好列表适合从高到低遍历，却不适合快速回答“i 更喜欢 a 还是 b”。预处理二维数组 rank[i][j]，表示 j 在 i 的偏好列表中的位置；位置越小，偏好越高。于是一次双向偏好判断只需 O(1)。

剪枝范围

对 x 来说，只需检查排在当前搭档 y 前面的朋友 u。一旦遍历到 y，后面的人都不可能比 y 更受 x 偏好，可以立即停止；找到一个有效 u 后，x 已确定不开心，也立刻停止。

完整过程

  1. 构建 rank：对每个 i 和偏好位置 pos，令 rank[i][preferences[i][pos]] = pos。
  2. 构建搭档数组 partner：若一对为 [a,b]，则 partner[a]=b 且 partner[b]=a。
  3. 逐个检查朋友 x，令其搭档为 y。
  4. 按 x 的偏好顺序扫描 u；扫描到 y 就结束当前人的检查。
  5. 令 v 为 u 的搭档。若 rank[u][x] < rank[u][v]，两项条件同时成立：答案加一，并停止检查 x。

正确性证明

若算法计入 x，则 x 确实不开心。

算法只从 y 之前选择 u，因此 x 更偏好 u 而非 y；又仅在 rank[u][x] < rank[u][v] 时计数，因此 u 更偏好 x 而非 v。两项定义均成立。

若 x 不开心，则算法一定计入 x。

按定义存在见证者 u，且 x 更偏好 u 而非 y，所以 u 必定位于 x 的列表中 y 之前，算法会扫描到它；第二项定义使比较成立，算法随即计入 x。

两方向合并可知，算法计数的集合与所有不开心朋友的集合完全相同，因此返回值正确。

时间复杂度O(n²)

构建 rank 以及最坏情况下逐人扫描偏好列表。

空间复杂度O(n²)

rank 矩阵占主导；partner 数组为 O(n)。

边界情况

  • n = 2：每个人的唯一选择就是当前搭档，不会不开心。
  • 搭档在某人的偏好列表第一位：没有更受偏好的人，直接判定该朋友开心。
  • 同一个 x 可能有多个见证者：找到第一个就停止，避免重复计数。
  • 不开心关系不要求 x 与 u 最终成对，也不要求配对之间按顺序出现。

class Solution {
    public int unhappyFriends(int n, int[][] preferences, int[][] pairs) {
        int[][] rank = new int[n][n];
        for (int i = 0; i < n; i++) {
            for (int pos = 0; pos < n - 1; pos++) {
                rank[i][preferences[i][pos]] = pos;
            }
        }

        int[] partner = new int[n];
        for (int[] pair : pairs) {
            partner[pair[0]] = pair[1];
            partner[pair[1]] = pair[0];
        }

        int answer = 0;
        for (int x = 0; x < n; x++) {
            int y = partner[x];
            for (int u : preferences[x]) {
                if (u == y) break;
                int v = partner[u];
                if (rank[u][x] < rank[u][v]) {
                    answer++;
                    break;
                }
            }
        }
        return answer;
    }
}

                    answer += 1
                    break

        return answer

替代方案

直接查找偏好位置：不建立 rank，每次用线性扫描比较 u 对 x、v 的偏好，会把最坏时间提高到 O(n³)，但额外空间可降到 O(n)。在 n ≤ 500 时，rank 方案更稳妥。

位集/图建模：可以先为每个人建立“比搭档更受偏好”的集合，再寻找双向边，本质仍是 O(n²) 预处理与扫描，表达通常不如 rank 直接。

常见错误

  • 只检查 x 是否偏好 u，忘记检查 u 是否也偏好 x。
  • 把偏好下标越大误认为越喜欢；实际是越小越喜欢。
  • 找到多个见证者时对同一个 x 重复计数。
  • 只按 pairs 的左端点检查，漏掉每对中的另一人。
  • 比较 rank[x][u] 与 rank[x][y] 后，又错误地用 x 的 rank 判断 u。

面试追问

为什么总时间不是 O(n³)？

rank 将任意一次偏好比较从 O(n) 降到 O(1)。外层最多 n 人，内层每人最多扫描 n−1 个候选，因此为 O(n²)。

能否不建立 partner 数组？

可以每次在 pairs 中查找搭档，但一次查询会变成 O(n)，从而拖累总体复杂度。partner 用 O(n) 空间换取 O(1) 查询。

为什么扫描到 y 就能停？

preferences[x] 已按喜好从高到低排列。y 后面的所有人都不如 y，因此不可能满足“x 更偏好 u 而非 y”。

不开心关系一定成对出现吗？

定义中的某次见证关系具有双向偏好，但某个人可能通过另一位朋友被判定。算法仍按“人”计数，每人最多一次。
