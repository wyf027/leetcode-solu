主动请求确认消息的用户

Users That Actively Request Confirmation Messages

同一位用户的两次请求，究竟离得有多近？
从请求记录里，找出在任意一个 24 小时窗口内至少请求两次确认消息的用户。

阅读题目时间轴实验测试与验证
01 / 题目与数据契约

只看请求时间，边界也算在内

输入为 Signups 和 Confirmations 两张表。输出一列 user_id：只要某用户有两条不同的请求记录，其时间差不超过 24 小时，该用户就应出现一次。结果顺序不限；消息最终确认还是超时都不影响入选。

Signups · 注册记录
列名类型
user_idint
time_stampdatetime

user_id 唯一；time_stamp 是该用户的注册时刻。

Confirmations · 请求记录
列名类型
user_idint
time_stampdatetime
actionENUM

约束与含义

  • Confirmations 的联合主键为 (user_id, time_stamp)；同一用户不会在完全相同的时刻有两条记录。
  • Confirmations.user_id 外键指向 Signups.user_id。
  • action 只取 confirmed 或 timeout，分别表示已确认或未确认而过期；time_stamp 记录的是请求时刻。
  • 24 小时是持续时间，含恰好 24 小时，不是“同一自然日”。
  • 公开题面未给出表行数、用户编号范围等数值上限，本页不虚构额外约束。

05 / 独立题解

先想一想，再打开解法

如何避免比较同一用户所有可能的请求组合？为什么不必检查确认结果？

题解：排序后，只检查相邻请求

核心洞察

对一个用户，将请求时刻排成 t₁ < t₂ < …。如果某一对请求相隔不超过一天，它们之间至少有一对相邻请求也相隔不超过一天。因此，只要检查每条请求与它的前一条，无须枚举所有组合。注册表只保证用户存在，action 无关，查询只需要 Confirmations。

完整过程

  1. 用 PARTITION BY user_id 分组，ORDER BY time_stamp 排序。
  2. LAG(time_stamp) 取同一用户的上一请求时刻。第一条没有前驱，跳过。
  3. 保留当前时刻不晚于“前一时刻 + 24 小时”的记录。
  4. DISTINCT user_id 去重，得到结果表。

示例中按用户编号依次处理：2 命中 86400 秒，3 命中 419 秒，6 命中 86399 秒，7 的 86401 秒未命中。演示逐条显示排序和前驱，SQL 由数据库执行相同的逻辑关系，并不保证物理执行顺序。

正确性证明

充分性：若相邻两条满足不超过一天，它们同属一个用户且由主键保证为不同请求，直接构成题目要求的一对，因此返回该用户合法。

必要性：假设合法的一对为 tᵢ、tⱼ（i < j）。排序保证 tᵢ₊₁ ≤ tⱼ，于是 0 < tᵢ₊₁ − tᵢ ≤ tⱼ − tᵢ ≤ 24 小时。扫描必能找到这对相邻请求。故不遗漏合法用户；DISTINCT 保证每人只出现一次。

边界与常见错误

  • 空表或某用户仅一条请求：没有有效前驱，不入选。
  • 恰好 24 小时必须包含；写成 < 会漏解。
  • 别用按日期的 DATEDIFF 或截断整小时的差值判断：24 小时多 1 秒可能被错误接受。
  • 不能把 action = 'confirmed' 当作条件，timeout 也代表发起过请求。
  • 不能跨用户比较，不能拿注册时间充当请求时间，不能用同一条记录与自己配对。
  • 多次命中只输出一次；至少两次不是恰好两次。
  • 本地参考使用统一的无时区时间语义，不把 SQL DATETIME 当成本地夏令时日历间隔。

复杂度

令 n 为请求数、u 为用户数。基于排序的实现通常需要 O(n log n) 时间；排序后扫描 O(n)。四语言参考存储分组时间共 O(n)，结果 O(u)。SQL 窗口排序和去重的资源开销依执行计划而定，通常需要 O(n) 级中间空间；若索引 (user_id, time_stamp) 可提供顺序，有机会减少排序成本，不能据此保证固定复杂度。

主解与四语言完整代码

本题是数据库题。主解使用官方支持的 MySQL（窗口函数需 MySQL 8+）。Java、JavaScript、Python、C++ 均为本地语义参考，接受完整的两表参数但无需读取 Signups，返回唯一用户 ID 列表；不应粘贴到 SQL 提交栏。Python 参考未采用元数据中的 Pandas 接口。

MySQL 8+ · 官方可提交 SQL

WITH ordered_requests AS (
    SELECT user_id, time_stamp,
           LAG(time_stamp) OVER (
               PARTITION BY user_id ORDER BY time_stamp
           ) AS previous_time
    FROM Confirmations
)
SELECT DISTINCT user_id
FROM ordered_requests
WHERE previous_time IS NOT NULL
  AND time_stamp <= previous_time + INTERVAL 24 HOUR;

Java · 本地语义参考

import java.time.LocalDateTime;
import java.time.Duration;
import java.time.format.DateTimeFormatter;
import java.util.*;

class Solution {
    // Each signup row: [user_id, time_stamp].
    // Each confirmation row: [user_id, time_stamp, action].
    // Returns unique IDs, not a SQL result table.
    public List<Integer> findRequestingUsers(
            List<List<String>> signups,
            List<List<String>> confirmations) {
        DateTimeFormatter fmt =
            DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");
        Map<Integer, List<LocalDateTime>> groups = new TreeMap<>();
        for (List<String> row : confirmations) {
            int id = Integer.parseInt(row.get(0));
            groups.computeIfAbsent(id, k -> new ArrayList<>())
                  .add(LocalDateTime.parse(row.get(1), fmt));
        }
        List<Integer> answer = new ArrayList<>();
        for (var entry : groups.entrySet()) {
            List<LocalDateTime> times = entry.getValue();
            Collections.sort(times);
            for (int i = 1; i < times.size(); i++) {
                long seconds = Duration.between(
                    times.get(i - 1), times.get(i)).getSeconds();
                if (seconds <= 86400) {
                    answer.add(entry.getKey());
                    break;
                }
            }
        }
        return answer;
    }
}

JavaScript · 本地语义参考

// Rows use the same column order as the official input.
// Returns unique user IDs. Inputs obey the database constraints.
function findRequestingUsers(signups, confirmations) {
  const groups = new Map();
  for (const [id, stamp] of confirmations) {
    // Interpret naive SQL timestamps on a fixed UTC timeline;
    // this avoids local daylight-saving adjustments.
    const time = Date.parse(stamp.replace(" ", "T") + "Z");
    if (!groups.has(id)) groups.set(id, []);
    groups.get(id).push(time);
  }
  const answer = [];
  for (const [id, times] of groups) {
    times.sort((a, b) => a - b);
    for (let i = 1; i < times.length; i++) {
      if (times[i] - times[i - 1] <= 86400000) {
        answer.push(id);
        break;
      }
    }
  }
  return answer;
}

Python · 本地语义参考（非 Pandas 提交签名）

from collections import defaultdict
from datetime import datetime, timedelta


def find_requesting_users(signups, confirmations):
    """Rows follow official column order; return unique IDs.

    Inputs obey the table constraints. Signups is intentionally unused.
    This is a standard-library semantic reference, not the Pandas API.
    """
    groups = defaultdict(list)
    for user_id, stamp, action in confirmations:
        groups[user_id].append(datetime.fromisoformat(stamp))
    answer = []
    for user_id, times in groups.items():
        times.sort()
        for previous, current in zip(times, times[1:]):
            if current - previous <= timedelta(hours=24):
                answer.append(user_id)
                break
    return answer

C++20 · 本地语义参考

#include <algorithm>
#include <chrono>
#include <map>
#include <string>
#include <vector>
using namespace std;

struct Signup { int user_id; string time_stamp; };
struct Confirmation {
    int user_id;
    string time_stamp;
    string action;
};

class Solution {
    // Input format: YYYY-MM-DD HH:mm:ss, valid SQL DATETIME.
    static chrono::sys_seconds parse(const string& s) {
        using namespace chrono;
        int y = stoi(s.substr(0, 4));
        unsigned m = static_cast<unsigned>(stoi(s.substr(5, 2)));
        unsigned d = static_cast<unsigned>(stoi(s.substr(8, 2)));
        return sys_days{year{y}/month{m}/day{d}}
             + hours{stoi(s.substr(11, 2))}
             + minutes{stoi(s.substr(14, 2))}
             + seconds{stoi(s.substr(17, 2))};
    }
public:
    vector<int> findRequestingUsers(
            const vector<Signup>& signups,
            const vector<Confirmation>& confirmations) {
        map<int, vector<chrono::sys_seconds>> groups;
        for (const auto& row : confirmations)
            groups[row.user_id].push_back(parse(row.time_stamp));
        vector<int> answer;
        for (auto& [id, times] : groups) {
            sort(times.begin(), times.end());
            for (size_t i = 1; i < times.size(); ++i) {
                if (times[i] - times[i - 1] <= chrono::hours{24}) {
                    answer.push_back(id);
                    break;
                }
            }
        }
        return answer;
    }
};

替代方案：自连接

将 Confirmations 与自身按用户连接，用严格时间先后排除自身配对，再限定后者在一天以内。无需窗口函数，但候选对最坏为 Σkᵤ² ≤ n²；合适索引可改善查找，密集请求仍可能产生大量匹配。

SELECT DISTINCT earlier.user_id
FROM Confirmations AS earlier
JOIN Confirmations AS later
  ON later.user_id = earlier.user_id
 AND later.time_stamp > earlier.time_stamp
 AND later.time_stamp <= earlier.time_stamp + INTERVAL 24 HOUR;

面试追问

  • 窗口改成任意 H 小时？相邻比较证明不变，只需改变阈值。
  • 要求 24 小时内至少 k 次？排序后比较 tᵢ 与 tᵢ₋ₖ₊₁，或使用双指针滑动窗口；只检查一对相邻值不再充分。
  • 需要实时处理？在每用户按时间到达的前提下，只记上次请求和是否已入选；乱序事件则要补充缓冲或乱序处理规则。
  • 如何选择 SQL 方案？结合数据库版本、联合索引、数据分布和执行计划评估窗口函数与自连接，不靠语法长度判断性能。
