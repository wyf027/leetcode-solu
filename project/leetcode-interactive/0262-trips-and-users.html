行程和用户

先同时排除被禁用的客户和司机，再按日期统计取消行程占有效行程的比例。

题意与 SQL 数据模型

Trips 保存订单：id, client_id, driver_id, city_id, status, request_at；Users 保存 users_id, banned, role。状态仅可能为 completed、cancelled_by_driver 或 cancelled_by_client。

对 2013-10-01 至 2013-10-03（含）每个至少有一笔行程的日期，计算：双方用户均未被禁用时，取消订单数 / 有效订单总数，并把 Cancellation Rate 四舍五入到两位小数。

官方结果

2013-10-01 → 0.33，2013-10-02 → 0.00，2013-10-03 → 0.50

关键语义

  1. 1. 客户 和 司机都必须 banned = 'No'；任一方被禁用的订单均不进入分母，也不进入分子。
  2. 2. status IN ('cancelled_by_driver', 'cancelled_by_client') 才计为取消。
  3. 3. 只输出给定日期窗口内实际存在有效行程的日期，而非补齐无行程的日历。

题解

默认隐藏；SQL 为 LeetCode 可提交主解，其他语言仅展示本地同义参考。

核心：两次连接 + 条件聚合

同一张 Users 表有两个身份：客户和司机。分别连接并把两方的 banned = 'No' 放入筛选条件。然后按 request_at 分组，COUNT(*) 是有效总数，条件 SUM 是取消数。

不要只过滤客户：被禁用司机的订单同样不合格。不要在 WHERE 中仅筛掉 completed：那会错误缩小分母。

完整过程：2013-10-01

  1. 1. 共 4 笔行程，其中 id=2 的客户被禁用，排除。
  2. 2. 剩下 3 笔有效行程，id=4 为 cancelled_by_client。
  3. 3. 取消率为 1 / 3 = 0.33，输出两位小数。

边界

某天所有行程都被排除时不应产生结果行；窗口之外的请求必须忽略；取消者是客户或司机都计入分子。

复杂度

数据库执行计划取决于索引；逻辑上扫描符合日期与用户条件的行程并分组。Trips(request_at) 和 Users(users_id) 有助于查询。

替代与错误

也可以用 AVG(status <> 'completed')（特定 DB 支持）；显式 SUM/COUNT 的语义更清晰。常见错误是忘记 ROUND 或忘记过滤司机。

面试追问

若要求补齐没有行程的日期，需构造日期表再 LEFT JOIN 聚合；这与本题“至少有一笔行程”的输出规则不同。 

SELECT
    t.request_at AS Day,
    ROUND(
        SUM(t.status IN ('cancelled_by_driver', 'cancelled_by_client')) / COUNT(*),
        2
    ) AS `Cancellation Rate`
FROM Trips AS t
JOIN Users AS client
    ON t.client_id = client.users_id AND client.banned = 'No'
JOIN Users AS driver
    ON t.driver_id = driver.users_id AND driver.banned = 'No'
WHERE t.request_at BETWEEN '2013-10-01' AND '2013-10-03'
GROUP BY t.request_at;
